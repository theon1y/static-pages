Обработка ввода на сервере

Как сервер превращает поток ненадёжных, иногда опоздавших или перепутанных пакетов ввода ровно в один шаг симуляции на игрока за тик, и как команды становятся действиями.

1. Сущность ввода

Каждый клиент создаёт один сетевой объект ввода (InputTemplate) в своей приватной группе доступа. В объекте хранится сетевой id игрока, которым он управляет. На сервере он становится отдельной сущностью рядом с игроком.

Создание
ReceivePlayerInputObjectSystem создаёт сущность ввода: PlayerMoveInput, PlayerTargetMoveInput, PlayerCommand (выключен), буфер PlayerInputHistory и TargetBattleObject с id игрока.
Привязка
ResolvePlayerInputTargetSystem каждый кадр резолвит этот id в сущность и записывает PlayerReference. Игрок может прийти позже объекта ввода или пересоздаться при респауне или реконнекте — привязка последует за ним.
Сохранение
Объект ввода принадлежит участнику и переживает дисконнект. При реконнекте клиент получает свой объект ввода обратно через ReceiveSelfPlayerInputObjectSystem и продолжает писать в него.

2. Приём пакетов

Клиент каждый тик отправляет NetworkPlayerInput по ненадёжному неупорядоченному каналу. В каждом пакете вся неподтверждённая история: только изменения плюс текущее движение на последнем тике.

// ReceivePlayerInputSystem
lastTick = packet.History[^1].Tick
if (buffer.Last.Tick > lastTick) return;   // старый пакет пришёл после нового: игнорируем
buffer.Overwrite(packet.History);           // новый пакет — надмножество старых

Сливать ничего не нужно. Последний пакет уже содержит всё неподтверждённое, поэтому потерянный или перепутанный пакет ничего не стоит, пока приходит следующий. Клиент обрезает историю, когда её подтверждает PlayerServerPosition.ClientInputTick.

3. Один шаг на серверный тик: ApplyPlayerInputSystem

Работает в FixedStepSimulationSystemGroup до намерения движения, прерывания движением и группы действий. Для каждого игрока хранит PlayerTicks:

ПолеСмысл
SimulatedTickКлиентский тик, которому сейчас соответствует серверное состояние игрока. Отправляется обратно вместе с позицией.
ClientInputTickПоследний клиентский тик, чей ввод применён. Никогда не опережает SimulatedTick. Подтверждает историю клиенту.
JitterBufferСколько тиков ввода придерживается во время простоя, чтобы у следующего действия ввод был наготове. От 0 до 4.
JitterBufferChangeTickКогда буфер менялся последний раз. Нужен для его уменьшения.

Продвижение

Затухание
Если буфер > 0 и не менялся 5 с (150 тиков), уменьшить его на один. Соединение стабильно, задержка возвращается вниз.
Опоздавший ввод
ClientInputTick = clamp(lastReceived, ClientInputTick, SimulatedTick). Ввод, пришедший для уже экстраполированных тиков, применяется сейчас, а не теряется.
Простой
Игрок простаивает, а следующий непустой ввод впереди: перепрыгнуть SimulatedTick на min(activeTick, lastReceived − JitterBuffer). Так лаг сбрасывается без симуляции пустых тиков, а ввод на размер буфера остаётся в очереди.
Обычно
Ввод на следующий тик пришёл: SimulatedTick + 1, ClientInputTick идёт следом.
Голодание
Игрок активен, а ввода на следующий тик нет: всё равно SimulatedTick + 1 с экстраполяцией последнего движения. ClientInputTick отстаёт, буфер растёт на один (максимум 4), тик изменения сбрасывается.

Простой — это когда нет идущего действия, нет ожидающей команды, нет живой цепочки от собственного действия игрока (EffectChainKey.ActionTick > 0), стик в мёртвой зоне (сила ≤ 0.1) и нет более новой цели клика. Пропуск тиков в любом из этих состояний сдвинул бы тайминги относительно предсказания клиента.

Применение

После продвижения по порядку применяются все записи истории с тиком в (старый ClientInputTick, новый ClientInputTick]. Когда сервер догоняет, за один серверный шаг может примениться несколько тиков:

ЗаписьЧто делает на сервере
MoveПерезаписывает PlayerMoveInput { Direction, Force, StartTick }.
TargetMoveПерезаписывает PlayerTargetMoveInput { Position, StopDistance, Force, StartTick }.
CommandВключает PlayerCommand { Action, Tick, SkillId | InteractionId | SeriesAttackType }. Резолвит сетевой id цели в сущность и пишет ActionTarget и на игрока, и на ввод. Для атак сбрасывает AttackCooldown, потому что тайминг серии на клиенте мог разойтись с серверным.

Тик без записи повторяет предыдущий ввод, так как записываются только изменения.

4. Ввод в движение

  • DisableTargetIntentByMoveInputSystem: активное движение стиком отменяет цель клика, если игрок не управляется аггро.
  • PlayerMoveIntentSystem: побеждает ввод с более новым StartTick. Стик становится MoveIntent с силой 0 или 1 по мёртвой зоне, цель — TargetIntent. Пропускается, если игрок мёртв или под контроль-блокером.
  • StopOnActionSystem обнуляет движение при входе действия в подготовку и во время каста, так же как на клиенте.

5. Команды в действия

Фильтр
ApplyPlayerCommandSystem (первая в ActionFixedStepSystemGroup). Если идёт действие и эта команда не может его прервать (InterruptUtils.IsInterruptedByRequest), команда отбрасывается.
Запрос
Собирает ActionRequest с тиком команды: Скилл: SkillUtils.RequestSkill, который заодно выбирает нужный скиллу пресет оружия. Взаимодействие: InteractActionUtils.RequestInteraction. Атака: AttackActionUtils.RequestAttack с таймингами серии, масштабированными скоростью атаки.
Старт
StartActionSystem проверяет и запускает CurrentAction. ActionTimerSystem и EndActionSystem ведут подготовку → каст → завершение.
Отказ
SendRejectedSkillCooldownSystem: если действие по команде скилла не стартовало на её тике, отправляется SkillCooldownNetworkEvent с реальным серверным кулдауном. SendInterruptedSkillCooldownSystem делает то же для скилла, прерванного на подготовке.
Поглощение
ConsumePlayerCommandSystem выключает PlayerCommand и ActionRequest игрока. Каждая команда применяется один раз.

Запрос несёт клиентский тик, поэтому действие, его броски рандома и его цепочки используют тот же action.Tick, что и предсказание клиента. См. Синхронизация рандома.

6. Ответ клиенту и побочные каналы

  • SendPlayerPositionSystem отправляет PlayerServerPosition { Position, SimulatedTick, ClientInputTick } только при изменении трансформа или тиков, по ненадёжному упорядоченному каналу.
  • Остальные игроки получают действие через NetworkActionRequest, а позицию — через обычный трансформ.
  • События в объект ввода, не относящиеся к тиковому вводу: PlayerEffectNetworkRequest (сервер создаёт цепочку на игроке, например от расходника) и PlayerResurrectNetworkRequest (сервер создаёт ResurrectRequest).
