Стало · авторитетный сервер, предсказание на клиенте

Как стало

Обе стороны идут одним фиксированным шагом: FixedStepTick, 30 тиков в секунду. Клиент отправляет ввод с номером своего тика. Сервер симулирует этот тик и сообщает, какому тику соответствует его состояние.

Какой мир что симулирует

КонтекстФичиПоведение
Выделенный сервер (UDS)CalculationAllowedСимулирует всех игроков и AI-юнитов. Игроки создаются из Self-префаба.
Клиент в рейде / лабиринте / PvPPrediction (+ сетевые системы)Предсказывает только своего игрока. Остальные игроки — интерполируемые реплики.
Клиент в хабеNetwork + CalculationAllowedВ хабе нет серверной симуляции, поэтому клиент остаётся авторитетным.
Локальное соло / без сервераCalculationAllowed (+ Network при записи реплея)Полностью локально, как раньше.

Задаётся в CalculationTagController. Системы фильтруются через WorldSystemFilter, поэтому большая часть геймплейного кода переехала из battle/Client в battle/Core и без изменений работает на обеих сторонах.

Один тик от начала до конца

Клиент
Запись. SendPlayerInputSystem добавляет запись в историю только при изменении ввода: Move, TargetMove или Command (атака / скилл / взаимодействие с тиком и целью).
Клиент
Предсказание. Те же системы из Core работают локально на Self-игроке. Позиция на этот тик записывается в PredictedPositionElement, до 90 тиков (3 с).
Сеть
Отправка. Вся неподтверждённая история плюс текущее движение, каждый тик, по ненадёжному неупорядоченному каналу. FixedList512Bytes вмещает 14 записей по 36 байт. Потерянный пакет покрывается следующим.Пакет пишется в объект ввода участника в приватной группе доступа, поэтому его видят только владелец и сервер.
Сервер
Применение. ApplyPlayerInputSystem продвигает PlayerTicks каждого игрока на один шаг (см. ниже) и применяет все записи истории до нового клиентского тика. Команда превращается в PlayerCommand + ActionTarget, сетевой id резолвится в сущность.
Сервер
Симуляция. Движение, действия, цепочки, урон. Всё авторитетно.
Сервер
Ответ. SendPlayerPositionSystem → PlayerServerPosition { Position, SimulatedTick, ClientInputTick } по ненадёжному упорядоченному каналу.
Клиент
Сверка. Удаляет историю ввода, подтверждённую ClientInputTick. Находит предсказание для SimulatedTick. Если расхождение больше 0.1 м, сдвигает текущую позицию и все последующие предсказания на величину ошибки.Коррекция — это смещение, без отката и пересимуляции.

Продвижение серверного тика: джиттер-буфер

Полный конвейер ввода на сервере →

На каждом серверном тике сервер выбирает для каждого игрока один из трёх шагов. Буфер растёт на один тик каждый раз, когда приходится экстраполировать, максимум до 4 тиков. После 5 секунд без экстраполяции он уменьшается на один тик. На стабильном соединении он остаётся равным 0 и не добавляет задержки.

Ввод пришёл414243→43Ввод на следующий тик уже есть — симулируем +1.
Ввод опоздал4142?→42Экстраполируем последний ввод и растим буфер. Когда 42 придёт с опозданием, он будет применён.
Простой + лаг4041424344→44Пропускаем пустой ввод, чтобы догнать, оставляя тики буфера в очереди.

Игрок не простаивает, пока идёт действие, ждёт команда или жива цепочка от его собственного действия (EffectChainKey.ActionTick > 0). Пропуск тиков в этот момент сдвинул бы такие цепочки относительно предсказания клиента.

Что ещё предсказывает клиент и как это исправляется

Урон

Предсказанные попадания записываются в PredictedHitElement с HitKey. Когда серверный DamageNetworkEvent приходит с тем же ключом, клиент корректирует здоровье на разницу, если она больше 5%. Предсказание без совпадения в течение 1.5 с откатывается.

Кулдауны скиллов

Если сервер отклонил команду скилла или прервал его на подготовке, он отправляет SkillCooldownNetworkEvent { SkillId, Tick, Remaining }. Клиент перезаписывает кулдаун и удаляет предсказанные цепочки этого тика действия.

Телепорты

DropPredictionOnWarpSystem очищает предсказанные позиции при WarpRequest. Иначе телепорт выглядел бы как огромная ошибка предсказания.

Плавная отрисовка

InterpolateFixedStepPositionSystem интерполирует между предыдущей и текущей позициями фиксированного шага внутри кадра. Скачки больше 1 м применяются сразу.

Другие игроки и побочные каналы

  • Удалённые игроки видят один NetworkActionRequest: действие, длительности, тик, цель и типизированные параметры в одной структуре. Self-юниты (предсказываемые) его игнорируют.
  • Запросы, не привязанные к тику, идут событиями в объект ввода: PlayerEffectNetworkRequest (расходники и подобное, цепочку создаёт сервер) и PlayerResurrectNetworkRequest.
  • Проверки дистанции на сервере допускают SyncSettings.AllowedDistanceError = 2 м на джиттер. Клиент проверяет точно в MoveToActionTargetSystem.
